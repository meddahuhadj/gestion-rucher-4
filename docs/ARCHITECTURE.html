MOUMEN Apiary AI — Architecture de la plateforme

Un copilote numérique pour l'apiculteur : voix, vision, texte et données réelles du rucher, réunis autour d'un assistant conversationnel. Ce document décrit les 23 volets d'architecture demandés au §65 du cahier des charges, puis la feuille de route MVP → production.

Frontend : React + TypeScript + Vite Backend : Node.js + TypeScript (Fastify) Infra : Supabase (Postgres · Auth · Storage) IA par défaut : Gemini 2.5 derrière AIProvider Devise : DZD / DA Langues : AR · FR · EN (RTL/LTR)
Partie A

Fondations

00Contexte & décisions de départ

Ce qui existe déjà

Un prototype fonctionnel mono-fichier (MOUMEN-ASSISTANT.html) : session temps réel avec l'API Gemini Live (gemini-2.5-flash-native-audio), capture micro + caméra dans le navigateur, transcription entrée/sortie, synthèse vocale, et function calling de démonstration (setAlarm, getWeather). La clé API est saisie côté client et stockée en localStorage.

Ce prototype valide la brique Voice + Vision temps réel. Il n'est pas la base de production : la clé API doit passer côté serveur, les données doivent être persistées, et les outils doivent être reliés à une vraie base métier. Le prototype devient la référence d'implémentation du module Voice.

Décisions de stack (validées)

DomaineChoixRaison
FrontendReact 18 + TypeScript + Vite + Tailwind + React RouterSPA installable en PWA, offline-first, pas de contrainte SSR. Écosystème mature pour Web APIs (média, IndexedDB).
BackendNode.js 20 + TypeScript + Fastify + PrismaLangage unique avec le frontend. Fastify : perf, schémas JSON natifs, streaming (SSE). Prisma : migrations typées.

Principes directeurs non négociables

Règle d'or

REAL DATA → REAL CONTEXT → AI REASONING → VALIDATION → USER CONFIRMATION → ACTION → AUDIT LOG

Aucune donnée critique (inspection, finance, reine, traitement, suppression) n'est créée ou modifiée sans validation de schéma, vérification des permissions et — au-delà de la lecture — confirmation explicite de l'utilisateur. Chaque écriture sensible produit une entrée d'audit.

  • AI-first, Voice-first, Vision-first, Field-first, Data-first, Offline-first — dans cet ordre de priorité produit.
  • Anti-hallucination (§35) — l'IA ne répond sur le rucher qu'à partir de données retournées par un outil. Donnée absente : « Je ne possède pas cette information dans vos données. »
  • Prudence sanitaire (§34) — jamais de diagnostic affirmatif. Toujours : observation → confiance → interprétation → à vérifier → recommandation.
  • Historique inviolable — soft delete uniquement, jamais de suppression en cascade silencieuse de l'historique d'une ruche.
Partie B

Architecture applicative

01Architecture Web complète

Application Web moderne, responsive, PWA, offline-first, multilingue. Trois couches lisibles : un client riche qui fonctionne hors-ligne, une API applicative sans état qui garde les secrets et orchestre l'IA, une plateforme de données managée.

Points structurants

  • Client autonome — toutes les opérations « terrain » (consulter, inspecter, observer, photographier, créer une tâche) fonctionnent sans réseau, contre IndexedDB. Voir §15.
  • API sans état — pas de session serveur ; tout le contexte transite par le JWT et le corps de requête. Scalable horizontalement, redémarrable sans perte.
  • Secrets côté serveur — aucune clé IA privée dans le bundle JS en production (§14). La voix temps réel utilise un jeton éphémère à courte durée émis par l'API.
  • Streaming — les réponses de MOUMEN arrivent en flux (SSE) pour un ressenti conversationnel.

02Architecture frontend

Architecture modulaire par feature. Chaque domaine métier est une tranche verticale autonome (composants, hooks, requêtes, types, store local). Les services transverses sont partagés.

Choix techniques

  • Data layer — TanStack Query pour le cache serveur + persister IndexedDB ; mutations optimistes qui écrivent d'abord dans la sync queue.
  • État global — Zustand pour le peu d'état vraiment global (utilisateur, statut réseau, contexte courant alimentant le Context Engine). Le reste est local à la feature.
  • Formulaires + validation — React Hook Form + Zod ; les mêmes schémas Zod valident côté client et sont dérivés des schémas d'outils IA.
  • Routing — React Router, lazy-loading par route, code splitting par feature.
  • Rendu terrain — un FieldShell distinct (gros boutons, contraste élevé, utilisable avec des gants) activé sur mobile ou via un interrupteur « Mode terrain » (§18/24).
  • Accessibilité — cibles ≥ 44px, focus visible, ARIA sur les composants interactifs, respect de prefers-reduced-motion, contrastes AA.

03Architecture backend

API Fastify découpée en modules métier + un noyau IA. Chaque module expose : routes (schéma JSON) → controller → service (logique + permissions) → repository (Prisma). Les tools IA réutilisent la couche service, ils ne dupliquent jamais la logique.

Conventions

  • Contrat unique — les schémas Zod/JSON sont la source de vérité ; l'OpenAPI et les types frontend en sont dérivés.
  • Permissions au niveau service — chaque méthode de service reçoit le userContext (id, rôle, org) et filtre/refuse en conséquence. La RLS Postgres est la seconde barrière.
  • Transactions — toute écriture multi-tables (inspection + observations + pièces jointes) est transactionnelle ; l'audit est écrit dans la même transaction.
  • Idempotence — les endpoints d'écriture acceptent un client_uuid pour absorber les rejeux de la sync queue.
  • Jobs — un worker séparé (même image) traite le cron : détection d'alertes (§13 fonctionnel), rappels, recalculs, sauvegardes.

04Architecture base de données

PostgreSQL relationnel, une seule base. Multi-tenant par owner_id (utilisateur) et, en V4, org_id (collaboration). Conventions transverses appliquées à toutes les tables :

  • Clé primaire id uuid default gen_random_uuid().
  • Horodatage created_at, updated_at (trigger), deleted_at nullable (soft delete).
  • Traçabilité created_by, owner_id ; client_uuid unique pour l'idempotence offline.
  • RLS activée partout : owner_id = auth.uid() (+ règles org en V4).
  • Intégrité — FK avec on delete restrict sur l'historique ; jamais de cascade destructif. Les statuts sont des enum Postgres ou des tables de référence.
  • Index — sur toutes les FK, sur (owner_id, deleted_at), et index temporels sur inspections(hive_id, performed_at desc).

Le schéma détaillé des 20+ tables est en §11. Les données IA (observations, recommandations, sessions de conversation) sont dans des tables dédiées, jamais mêlées aux données saisies par l'apiculteur — la distinction données enregistrées / observations IA / recommandations IA est structurelle.

Partie C

Le cerveau MOUMEN

05Architecture MOUMEN AI

MOUMEN n'est pas un chatbot isolé posé à côté du CRUD : c'est la couche d'interaction principale. Trois entrées (voix, vision, chat) convergent vers un orchestrateur unique qui raisonne sur des outils reliés à la base métier.

Sous-systèmes

Intent Engine

Classe la demande (lecture / action / analyse / navigation) et la route. Résout les références déictiques (« elle », « cette ruche ») avec le contexte de page.

Context Engine

§10 — assemble utilisateur, rucher/ruche courants, date, événements récents, tâches, historique, météo disponible.

AI Orchestrator

§8 — boucle plan → appels d'outils → validation → confirmation → réponse + audit.

Tool Registry

§9 — ~40 outils à schéma strict, chacun avec niveau de confirmation et contrôle de permission.

Apiary Knowledge Engine

Couche métier séparée : seuils (reine « ancienne », inspection « en retard »), règles saisonnières, vocabulaire apicole. Configurable par l'utilisateur.

Guards

Anti-hallucination, prudence sanitaire, politique de confirmation. S'appliquent après le raisonnement, avant la réponse et l'action.

06Architecture Voice

Conversation vocale naturelle dans le navigateur : micro → transcription → raisonnement → réponse parlée, avec interruption (barge-in) et détection de parole. Deux modes selon la latence recherchée.

Composants

  • Capture — getUserMedia, AudioContext 16 kHz, ScriptProcessor/AudioWorklet → PCM base64 (repris du prototype).
  • VAD — détection d'activité vocale locale pour ne streamer que la parole et gérer le barge-in.
  • Lecture — file de buffers 24 kHz avec nextStartTime (repris du prototype) ; interrupted vide la file.
  • Langue — sélectionnée par l'utilisateur (AR/FR/EN) ; passée dans la config de session et le TTS.
  • Fallback — hors connexion ou navigateur non compatible : SpeechRecognition/SpeechSynthesis Web + raisonnement en différé (mode texte). L'UI l'indique.
  • Sécurité — jamais la clé API dans le client : jeton éphémère à portée réduite, révocable, journalisé (§14).
  • Historique — chaque session écrit conversation_sessions + conversation_messages (transcript, outils appelés, durée).

07Architecture Vision — MOUMEN VISION

Accès caméra après autorisation explicite. Trois modes : Live camera, Import d'image, Analyse IA. L'analyse ne produit jamais un diagnostic : elle produit une structure prudente.

Cibles d'analyse (quand techniquement possible)

Ruche, cadres, abeilles, couvain, entrée, réserves, reine si visible, équipements, anomalies visuelles potentielles.

Prudence — §34

Jamais « cette ruche a telle maladie ». Toujours « une anomalie visuelle potentielle a été observée, une vérification humaine est nécessaire ». Formulations imposées : observation potentielle, indice, estimation, probabilité, à vérifier, information générale.

08AI Orchestrator

Couche centrale qui transforme une demande en langage naturel en actions validées. Boucle bornée (max N itérations d'outils) et entièrement journalisée.

Responsabilités

  • Contexte & mémoire — fenêtre de conversation + mémoire métier via le Knowledge Engine ; pas de mémoire cachée hors base.
  • Permissions — chaque appel d'outil est ré-autorisé côté serveur, indépendamment de ce que le modèle « croit » pouvoir faire.
  • Validation — paramètres (Zod), cohérence métier (ruche existe, appartient à l'utilisateur), fenêtre temporelle plausible.
  • Confirmation — voir §23 fonctionnel ci-dessous ; l'orchestrateur renvoie une proposition d'action que le client doit confirmer avant exécution réelle.
  • Erreurs — un échec d'outil est renvoyé au modèle en tant que résultat (pas d'exception silencieuse) ; après N échecs, réponse honnête d'impossibilité.
  • Observabilité — chaque tour : tokens, latence, outils, coût estimé → métriques (§50 fonctionnel).

Confirmation des actions — §23

NiveauPortéeComportement
1 · lecture« Combien de ruches ai-je ? », résumés, statistiquesExécution directe, aucune confirmation.
2 · action réversibleCréer une inspection, une tâche, une observation« Je vais créer une inspection pour la ruche 12. Confirmer ? » — accord requis.
3 · action sensibleSuppression, modification importante, opération financière, action irréversibleModale de confirmation explicite : [ Annuler ] [ Confirmer ]. Jamais d'exécution implicite.

10Context Engine

Construit automatiquement le contexte à chaque tour, pour que l'utilisateur n'ait jamais à répéter où il se trouve. Depuis la fiche de la ruche 12, « ajoute une observation : elle est forte aujourd'hui » est compris sans question.

  • Origine — le client fournit page, currentApiary, currentHive (état global Zustand) ; le serveur complète events/tasks/historique/météo avec des données vérifiées.
  • Portée — le contexte est passé à l'orchestrateur mais filtré par permissions avant d'atteindre le modèle.
  • Fraîcheur — recomposé à chaque message ; jamais mis en cache au-delà d'un tour.
  • Absence — un champ inconnu vaut null, jamais une valeur par défaut inventée (météo notamment).

Partie E

Sécurité & accès

13Authentification

  • Fournisseur — Supabase Auth : email + mot de passe, magic link, OAuth Google. JWT signé (RS256), access_token court (~1 h) + refresh_token rotatif.
  • Stockage client — tokens en mémoire + refresh_token en cookie HttpOnly Secure SameSite=Lax (pas de token d'accès dans localStorage).
  • Vérification API — plugin Fastify qui valide la signature JWKS Supabase, charge userContext (id, rôle, org), et l'injecte dans la requête + le contexte RLS Postgres (set local role / request.jwt.claims).
  • RBAC — rôles owner / manager / viewer (extensible V4 multi-utilisateurs). Permissions granulaires par ressource (inspections:write, finance:read…), vérifiées au niveau service et pour chaque appel d'outil IA.
  • Offline — l'app reste utilisable avec un access_token expiré tant qu'elle est hors-ligne (lecture/écriture locales) ; au retour du réseau, refresh puis /sync/batch. Échec de refresh → écran de reconnexion, données locales préservées.
  • Voix — jamais le JWT applicatif envoyé à Gemini : /ai/voice/token émet un jeton éphémère dédié, portée voice, ~60 s, journalisé et révocable.

14Sécurité

Transport

HTTPS/HSTS partout. CORS restreint aux origines connues. En-têtes : CSP stricte, X-Content-Type-Options, Referrer-Policy, Permissions-Policy (caméra/micro limités à l'app).

Secrets

Aucune clé IA privée dans le bundle JS en production. Tous les appels IA sensibles passent par le backend. Secrets en gestionnaire (Doppler / SOPS / secrets de la plateforme), jamais en repo.

Entrées

Validation double : Zod côté client + Zod côté serveur. Prisma = requêtes paramétrées (anti-injection). Uploads : type MIME vérifié, taille limitée, EXIF GPS retiré, antivirus optionnel.

Débit

Rate limiting par IP + par utilisateur ; quotas spécifiques sur /ai/* (coût). Back-pressure sur le streaming.

Données

RLS Postgres sur toutes les tables. Chiffrement au repos (Supabase). Champs sensibles (notes financières) chiffrés applicativement si requis. Sauvegardes quotidiennes + test de restauration.

Traçabilité

audit_logs sur toute action importante (qui, quoi, avant/après, via ui/ai/sync/job). Logs applicatifs sans données sensibles (§50).

Fichiers

Storage privé par défaut ; accès via URL signée à courte durée, portée à l'utilisateur propriétaire.

IA

Garde-fous d'orchestration (§8) : permissions ré-vérifiées, confirmation niveau 2/3, anti-hallucination, prudence sanitaire. Prompt-injection : le contenu utilisateur/vision n'est jamais traité comme instruction système.

Partie F

Terrain & résilience

15Architecture offline

L'application doit fonctionner avec une connexion faible ou absente. Le client possède sa propre base locale ; le réseau n'est qu'un moyen de synchroniser.

Opérations garanties hors-ligne

Consulter les ruches et l'historique, créer une inspection, ajouter une observation, prendre une photo, créer une tâche. Ces écritures vont dans IndexedDB + sync_queue et sont visibles immédiatement (mutation optimiste).

Bandeau

🟠 Mode hors connexion — Vos données sont enregistrées localement. Synchronisation automatique dès que la connexion revient.

Une inspection enregistrée localement n'est jamais perdue : elle reste dans la queue jusqu'à confirmation serveur, même après fermeture de l'app ou redémarrage de l'appareil.

16Synchronisation

  • Versionnage — colonne version int incrémentée à chaque écriture serveur ; le client envoie la base_version sur laquelle il a travaillé.
  • Doublons — client_uuid unique en base : un rejeu ne crée jamais de seconde ligne.
  • Ordre — la queue respecte les dépendances de FK ; un échec bloquant met en pause la branche concernée, pas toute la queue.
  • Partiel — un batch peut être appliqué à moitié ; la réponse est explicite, la queue conserve le reste.
  • Conflits — jamais résolus silencieusement sur des données critiques : l'utilisateur voit « version locale / version serveur » et tranche.

17PWA

  • Manifest — nom, icônes maskables (192/512), display: standalone, theme_color, start_url, orientation libre, raccourcis (Nouvelle inspection, MOUMEN, Ruche active).
  • Service Worker — Workbox : précache de l'app-shell au build, stratégies par route (§15), skip waiting contrôlé + invite « Nouvelle version disponible ».
  • Installation — capture de beforeinstallprompt, bouton « Installer l'application » ; splash screen généré depuis le manifest.
  • Offline — page de repli, bandeau d'état réseau, file de synchro visible dans Paramètres.
  • Notifications — Web Push quand supporté (alertes, rappels de tâches) via le worker de jobs ; dégradation propre si refusé/non supporté.
  • Comportement natif — une fois installée : plein écran, retour arrière géré, persistance du stockage demandée, accès rapide caméra/micro.

20User flows

Flow principal — la tournée

Flow — question en langage naturel

« Quelles ruches n'ont pas été inspectées depuis 15 jours ? » → Intent = lecture → searchApiaryData traduit en filtre sûr → getHives(not_inspected_since=15d) → réponse listée avec dates réelles. Donnée absente → « Je ne possède pas cette information dans vos données. »

Flow — inspection hors-ligne puis synchro

Au rucher sans réseau : l'inspection + 4 photos sont écrites dans IndexedDB + sync_queue, visibles immédiatement. De retour : refresh du token → POST /sync/batch ordonné → photos uploadées vers Storage → inspection liée → Timeline serveur à jour → autres appareils notifiés via Realtime.

Flow — planificateur de semaine

« Organise mon travail pour cette semaine » → POST /planner/generate agrège tâches en retard, inspections dues, ruches à surveiller, traitements et récoltes prévus, disponibilité → renvoie un planning proposé. Aucune tâche importante n'est créée sans confirmation (niveau 2).

Observabilité (§50)

  • Logs structurés (pino), corrélation par request_id, sans données sensibles.
  • Erreurs — Sentry front + back.
  • Métriques — latence/erreurs API, métriques IA (tokens, coût, taux d'échec d'outil, taux de confirmation refusée), santé de la synchro (âge de la queue, conflits).
  • Perf — Web Vitals réels ; budgets (§48) : lazy-loading, code splitting, compression d'images, pagination, listes virtualisées, debounce. Cible : fluide avec des centaines de ruches et des milliers d'inspections.

22Architecture de déploiement

  • Frontend — build statique déployé sur CDN (Vercel/Netlify/Cloudflare Pages), immuable, versionné.
  • Backend — image Docker unique (API + worker via commande), déployée sur Fly.io/Railway/VPS ; horizontalement scalable car sans état.
  • DB — Supabase managé au départ ; chemin de sortie vers Postgres auto-hébergé documenté (RLS et schéma sont standards).
  • Migrations — Prisma Migrate en étape CI dédiée, avant le basculement de trafic.
  • Config — 12-factor : tout par variables d'environnement (voir annexe).
